# Experimental Background TikTok Harvester

An unpacked Chrome Manifest V3 research prototype that asks for explicit TikTok site access, covers a logged-in desktop For You page, and experimentally sources a local pool of account-personalized video IDs while the TikTok tab is in the background. A complete pool is presented one video at a time through TikTok's official embed player.

This directory is standalone. It has no oTree integration, backend, upload endpoint, external JavaScript dependency, or build step.

## Research interpretation and limitation

The stimuli are an account-personalized pool produced under automated feed advancement. They are **not** the participant's natural FYP sequence. Chrome throttles hidden tabs and TikTok may stop hydrating a virtualized feed, so background collection is not guaranteed. The collector keeps every safely confirmed recommendation it can source during its locked wall-clock window. It opens the viewer at the deadline if at least one video was confirmed; an empty or structurally failed run opens no viewer.

Automatic advancement can affect the participant's future recommendations. TikTok receives ordinary page activity generated by its own site while the covered feed advances and may interpret brief watch time and skips as ranking signals. The extension does not claim to reproduce a neutral API request for “the next FYP video.”

## Install as an unpacked extension

1. Open `chrome://extensions` in desktop Chrome.
2. Turn on **Developer mode**.
3. Select **Load unpacked**.
4. Choose this `tiktok-fyp-pilot/` directory—the directory containing `manifest.json`.
5. Pin **TikTok FYP Research Pilot** from Chrome's Extensions menu.

After editing the source, use **Reload** on `chrome://extensions` before testing again. No package installation is needed to run the extension.

## Participant flow

1. Begin on the experiment page or another tab that should regain focus.
2. Open the extension popup. Optionally set the wall-clock sourcing window; the default is 30 seconds.
3. Read the disclosure, check consent, and select **Allow access and start**. Chrome requests only optional access to `https://www.tiktok.com/*`; the required `alarms` permission supplies a local deadline wake-up and grants no site data access.
4. The extension opens or reloads `/foryou`. A document-start opaque overlay covers the entire page before the collector initializes. TikTok remains rendered underneath it.
5. Once initialized, the extension returns to the originating tab. The covered TikTok tab attempts the harvest in the background.
6. Success focuses the existing minimalist viewer. Failure focuses the still-covered TikTok tab with **Try a fresh session** and **Stop and uncover TikTok** controls.
7. In the centered viewer, the participant presses **Play** once. Later videos attempt to autoplay and advance after a validated end. The compact bar supports pause/resume, previous/next, and Finish; arrow keys, up/down keys, Page Up/Page Down, Space, and mouse-wheel navigation are also available. Browser policy or TikTok may still require another Play click.

TikTok authentication remains entirely between Chrome and TikTok. The extension never attempts to bypass a login prompt, CAPTCHA, rate limit, or unsupported page state.

## Harvest protocol

The collector uses `MutationObserver` and chained `setTimeout` callbacks rather than `requestAnimationFrame`, so it can continue to receive opportunities in a hidden tab. It records actual timer delay and visibility because Chrome may throttle those callbacks.

For each step it:

1. Identifies one current feed driver and a uniquely identified offscreen successor.
2. Classifies the driver as `automation_driver`; a driver can never enter the viewer.
3. Durably writes the successor as `prepared` while it is still fully below the viewport.
4. Rechecks the DOM. If it is no longer unique, connected, ahead, below the viewport, and non-overlapping, the prepared record is invalidated.
5. Conceals the structural card with a tombstone while leaving the node mounted for TikTok's virtual scroller.
6. Confirms the concealment, which changes the record to `reserved` and makes it viewer-eligible.
7. Waits at least 750 ms for replacement hydration. If no replacement appears, it programmatically advances the relevant scroll container.

A stage may attempt advancement three times and has an eight-second limit. The entire session has a locked wall-clock window, backed by a one-shot extension alarm in case the hidden page's timers stop. Chrome documents that alarms may themselves be delayed—for example while the device sleeps—so “30 seconds” is a deadline target, not a hard real-time guarantee. At the deadline, all confirmed reservations become the viewer pool. A zero-video window, stage failure, unsupported page, target-tab closure, or safety-write failure changes the session to `failed`; explicit failures invalidate the partial bank and open no viewer.

Numeric IDs in ambiguous multi-ID card boundaries are excluded without concealing the broad container. Tombstones are reapplied after DOM recycling. Any other exact `/foryou` tab receives guard-only behavior for existing tombstones but cannot collect or display the overlay.

## Overlay behavior

The bound TikTok page receives a full-viewport host at the highest practical stacking level and a closed Shadow DOM interface. A document-start bootstrap mask covers the short interval before that interface mounts. The overlay is opaque and blocks participant pointer, wheel, touch, and keyboard input from reaching TikTok; only its own controls remain interactive.

Every underlying `<video>` and `<audio>` element is muted during harvesting. The extension remembers its prior muted/paused state and restores that state after the collector is shut down. The feed is kept rendered under the overlay because hydration and virtual scrolling depend on TikTok's DOM remaining present.

The originating experiment tab is remembered only as a transient numeric tab ID in `chrome.storage.session`. Its URL and title are never stored.

## Local data and migration

Schema version 3 is stored in `chrome.storage.local`. It contains only:

- a random local session ID and 32-bit selection seed;
- locked harvest-window duration;
- numeric video ID, classification, feed order, timestamps, and legacy active-watch milliseconds;
- prepared/reserved/invalidated state, tombstones, and viewer order;
- harvest phase plus bounded visibility, timer-delay, hydration-latency, and advancement diagnostics; and
- validated viewer playback events and local idempotency sequences.

Completed schema-1 sessions migrate as `legacy_manual`. Completed schema-2 background sessions are preserved. A schema-1 or schema-2 session still collecting is stopped with `collection_rule_replaced`; it is never silently continued under the new maximize-through-deadline rule.

The extension does **not** store usernames, creator names, descriptions, captions, account URLs, credentials, cookies, Prolific IDs, participant identifiers, or page content. There is no upload or export endpoint. TikTok's page and official player still communicate normally with TikTok.

The read-only **Local data** inspector displays the stored fields and bounded diagnostics. **Clear collected data** removes all sessions while retaining settings and permission. **Revoke TikTok access** shuts down collectors, unregisters the dynamic script, and removes the optional host permission while preserving stored records. Use both for no records and no access.

## Viewer boundary

Only records in confirmed `reserved` state enter the queue, once each and in interception order. A `prepared` or invalidated item cannot appear. The viewer creates only the current iframe using:

`https://www.tiktok.com/player/v1/{numeric_video_id}`

Description, music information, progress UI, and native controls are hidden through documented player parameters. After the first participant Play gesture, later iframes request autoplay and the host also sends TikTok's documented play command. Chrome or TikTok may reject autoplay, in which case the compact Play control remains available. All player messages must have the exact TikTok origin, the current iframe's `contentWindow` as source, the TikTok player marker, and an allow-listed event/value shape.

Private, deleted, region-restricted, or otherwise unavailable embeds may fail. That failure is stored locally and the participant can continue.

## Verification

Node 18 or newer is sufficient; there are no test dependencies.

```sh
npm run check
npm test
```

The suite covers schema migration, locked settings, maximize-through-deadline completion, empty-window failure, hidden timer diagnostics, deterministic selection, automation-driver exclusion, prepare-before-conceal semantics, confirmation, invalidation, tombstones, origin-tab return, retry, storage restoration, viewer ordering/skips, strict message validation, narrow permissions, and static overlay/state-machine guards.

Open **Local data → Open synthetic harness** and select **Run background-harvest assertions** to exercise hidden timing, replacement hydration, scroll-fallback diagnostics, three-attempt failure, retry, DOM recycling, tombstones, and the two-phase reservation protocol without a TikTok account. The fixture does not prove compatibility with TikTok's current live DOM.

Use [MANUAL_TEST_CHECKLIST.md](MANUAL_TEST_CHECKLIST.md) for logged-in Chrome trials. Do not call the collector operationally ready until those trials pass on the intended Chrome/TikTok versions.

## Main files

- `manifest.json` — MV3 permissions, entry points, and extension CSP.
- `background.js` — serialized state, dynamic registration, transient return-tab leases, failure/retry, permissions, and message authorization.
- `lib/core.js` — schema-3 model and pure selection, classification, reservation, migration, viewer, and validation logic.
- `content/dom-adapter.js` — conservative post-ID and bounded feed-card discovery.
- `content/collector.js` — Shadow DOM overlay, media/input isolation, automated hidden-tab state machine, tombstones, and diagnostics.
- `viewer/` — centered official TikTok iframe player, autoplay fallback, and bidirectional participant controls.
- `popup/`, `options/`, and `inspector/` — consent, settings, session status, and local records.
- `harness/` and `tests/` — synthetic fixture and dependency-free coverage.

## Deployment boundary

This is a local desktop research prototype, not a Chrome Web Store release or Prolific-ready pipeline. Any later transmission of records requires a separate privacy, consent, security, retention, IRB, and platform-policy design.
